# Changelog

## Unreleased

- **The map in German, and room for more languages:** the map's own words (buttons, panels, tooltips, messages, the tour and the glossary) now come from a language table in `skills/floorplan/assets/lang/`, and a German one is included. Add `"lang": "de"` to `floorplan/architecture.json`, or build once with `--lang de`, and Claude or Codex write the map's names, descriptions, flows, tour and recent work in German too, and answer questions in it. English stays the default and looks exactly as before. Adding a language is one file; see [Languages](docs/i18n.md).
- **Names that stay put:** an optional `floorplan/names.json` holds your own names (and, if you like, descriptions) for parts, files and endpoints, as one text or one per language. The build applies it last, so it wins over `architecture.json` and `descriptions/`, and a name in it that's no longer on the map is an error with a "did you mean …". `describe.mjs` leaves those entries alone, and `refresh.mjs` never moves them: it says which fixed files moved or went away. After a first map, Claude or Codex offer to freeze the names they chose. Without the file, nothing changes.
- **Who writes where:** an optional `floorplan/targets.json` lists the databases, services, files, APIs and queues your app writes to or reads from, the parts that write to each and the ones that only read, and whether a target allows one writer only. The map draws writes and reads as their own kinds of line (a read is dashed) from each part to the target's box, and a **Targets** panel lists every target with its writers and readers as tiles that lead to the map. A one-writer target with more writers turns red, on the map too, with an important Health finding and a fix; calls the scan saw into a target from parts the list leaves out are a minor finding, with POST, PUT, PATCH and DELETE read as writes and GET as reads (the scan now records the method of calls to outside services). Without the file, nothing changes.
- **Layers, and what keeps your code from being published:** an optional `floorplan/layers.json` sorts every file, by patterns, into the system you could publish one day, the setup of this one installation, and your own content; a part takes the layer most of its files have, or is mixed. A **Layers** switch in the top bar colours every box by its layer (with a tag, and a dashed ring for a mixed part), the details name each file's layer, and the legend shows one layer at a time. Health gets a **Publishability** group of its own, counted apart from the other findings: ids of one installation (UUIDs, long hex ids and generated-looking codes), contact details and absolute paths of one computer in system code, words from a private list of customer, people and place names in the system and the setup, and system code that imports content. Every finding names the file and the line, never the value, and a private word only by its first letter; the word list stays outside the repo, and without it that check is skipped with a note. The scan now records the line of each import (JavaScript imports were placed one line early). Without the file, nothing changes.
- **The map as text for AI workers, and inputs you can commit:** every build now writes `floorplan/MAP.md`, the map as plain text in the map's language: the project and its numbers, every part with its key files (up to 12, the most connected first, each with its name and one sentence) and endpoints, who writes where, the flows, the Health findings as a title and a count each (never a place or a value) and the recent work, in at most 1,500 lines (a list that would not fit ends in "… and N more"). The file is written again only when its text changes. An optional `"git": "inputs"` in `architecture.json` makes the folder's own `.gitignore` ignore only what a build writes again, so the inputs (`architecture.json`, `descriptions/`, `names.json`, `targets.json`, `layers.json`, `plan.json`, `custom-flows.json`) and `MAP.md` can be committed; a worker in such a project starts with `MAP.md` (`status.mjs` and the note in `CLAUDE.local.md` say so), a fresh clone is turned into a map with `refresh.mjs`, and `recent.mjs` leaves the folder's own files out of the changes it lists. Floorplan never commits anything itself. Without the field the folder still ignores itself completely, with the same `.gitignore` as before; the only difference is the extra `MAP.md` in it ([format](skills/floorplan/references/schema.md#git)).
- **What's running, from your own tooling:** an optional `floorplan/ops.json`, written by your cron, pipeline or deploy script (never by Floorplan or the AI), reports a status per part, file, endpoint or target (`ok`, `warn`, `down`, `unknown`), the deployed version, the last run, the last good run, the last error, a note and a few numbers, with the time it was written. The build checks it like recent work (a ref that isn't on the map is left out with a warning, a bad field is a warning, a file older than a day is stale) and reports `OPS  N items: …`. An **Ops** switch in the top bar gives every box with an entry a status dot (a part shows the worst status inside it), the hover and the details show the version, runs and error, and an **Operations** panel lists everything worst first with a click to each box, the time of the data and a stale warning. A map served by `serve.mjs` fetches the file again every minute, so the tooling can rewrite it between builds; a static copy keeps what the build saw. `MAP.md` never mentions it, an export carries it only with `--include ops`, and with `"git": "inputs"` the folder ignores it. Extensions can now add lines to a card's hover tooltip (`addTipSection`). Without the file, nothing changes.
- **Rules and decisions, hung on the map:** an optional `floorplan/rules.json` lists the rules a project documents ("one writer per target", "the AI delivers data, the code decides") and its dated decisions, each with the place it is written down, and the parts, files, endpoints and targets it applies to (a rule with no places holds everywhere). The build checks it like `targets.json` (an unknown ref, field, kind, status or date is an error with a "did you mean"), resolves each ref and reports `RULES  N rules, M decisions · K retired`. A **Rules** button on the map lists them, the ones that hold everywhere first and the retired ones dimmed at the end; a rule opens with its text, source and places as links and puts its cards on a board; every card the rules reach shows **Rules here** in its details. Health gets a minor finding, "Retired rule still applied", for a retired rule that still names places. `MAP.md` gets a `## Rules` section after Targets (one block per rule: kind, dates, places, text, source), so a committed map now changes once. Claude and Codex write the file only from what the project documents and never invent a rule. Without the file, nothing changes.
- **The Clock: what a schedule starts, and when.** The scan now finds the schedules in a codebase, from the files that hold them: `on.schedule` crons in GitHub Actions workflows, `crons` in `vercel.json`, n8n workflows with a Schedule Trigger or Cron node (their HTTP Request nodes as what they call), crontab files (`crontab`, `*.cron`, `cron.d/*`, with `CRON_TZ`) and ofelia labels in docker-compose files, and lists them with an id each (`SCHEDULES  N found`). An optional `floorplan/schedules.json` says what each one runs, gives one a better title or a note, switches off a find that no longer runs, and adds the schedules the scan can't see, each with its source; the build checks it like `rules.json` (an unknown ref or field is an error with a "did you mean", a cron that isn't five fields a warning), puts every cron into words in the map's language ("every 20 minutes", "daily at 02:30", "weekdays at 08:00", "every Sunday at 03:00", "monthly on the 1st at 06:00"), works out the start minutes of one day, draws an `event` line from a schedule's trigger to what it runs when both are on the map, and reports `SCHEDULES  N (a found, b declared) · next: …`. A **Clock** switch on the map marks every card a schedule starts (the plans on hover) and opens a panel with a 24-hour strip, a mark for every start, and the list, next start first, the switched-off plans dimmed at the end; a plan opens with its details and puts its cards on a board, and every card a schedule reaches shows **Schedules here**. `MAP.md` gets a `## Schedules` section after Rules, one line per plan. Floorplan never makes a time up. Without a find and without the file, nothing changes.
- **What you see: flows from the owner's side.** A flow in `architecture.json` can now say what starts it (`trigger`: a click, a clock, a message, a webhook, a file, a hand, in plain words, with the node it starts at or the id of a schedule from the Clock, whose words it then shows), what the owner sees at a step (`you_see`: the place, one sentence, a short example) and what they have in the end (`outcome`), each at a place on the map, usually an outside service like a phone, a calendar, a database or a mailbox. The build checks the refs like a flow's steps (an unknown place, node, schedule, kind or field is an error with a "did you mean"), keeps it all in `graph.flows`, turns it round into `graph.outcomes` (per place, what arrives there and from which flow and step) and reports `FLOWS  N · with trigger a · with outcome b · outcomes at c place(s)`. On the map the flow list and the guided view show the trigger ("Starts when: …", a clock with the schedule's words), an eye card with what you see at a step and its example, and "In the end: …" at the last step; a **What you see** button opens a panel with every place and what arrives there, a sentence opening the flow at that step, and a place's card lists **What arrives here**. `MAP.md` gets a `Trigger:` and a `You see:` line per flow and a `## What you see` section after Flows, so a committed map changes once. Claude and Codex write it from the owner's side ("A message on your phone with the customer's name", never "sends the Telegram payload"). Flows without the fields look exactly as before.
- **The map's lookups know the other floors:** `floorplan/query.mjs` and the Ask tools answer from them, once a project filled them in: `targets [words]` lists who writes where (every target with its box, writers and readers as cards with names, and one-writer conflicts), `rules [words | id]` the rules and decisions, by words or at one place (a part, file, endpoint or target: the rules that name it, its file, its part or a parent, each with the card it reaches it through, then the project-wide ones), `schedules` what a clock starts (cron in words, time zone, trigger, what runs, and the next start of the day), `ops [id]` what is running as the owner's tooling reported it (worst first with the time of the report, or one place with everything inside it and the worst status), `outcomes [id]` what you see at each place and from which flow, and `flows` every flow with what starts it and what you have in the end. `show` now lists the floors at a card (`rulesHere`, `targetsWritten`, `targetsRead`, `schedulesHere`, `ops`, `youSeeHere`) and `overview` counts them under `floors`, each with the query that lists it. The Ask instructions, the note in `CLAUDE.local.md` and `--help` name the commands, one line per floor, so an agent asks the map ("who may write to the orders table", "which rule holds here", "is the worker up") before it greps. A map without the files answers exactly as before, plus empty lists.
- **An edge between two outside services no longer breaks the board:** an edge in `architecture.json` from one external node to another (a database that notifies a mail service, a sign-in provider that calls a hosting platform) made the layout fail with "layer constraint set to LAST", because every external node sits in the last column. The build keeps such an edge and warns (`edges[i]: both ends are external nodes; shown in the panels, not drawn on the board`), marks it `drawn: false` in `graph.json`, and the map leaves it out of the layout while the details of both nodes still list it.
- **The Health findings in the map's language:** the titles, explanations and card notes of every finding (secrets in the code, settings files in git, keys sent to the browser, Supabase tables and Firebase rules anyone can reach, Stripe webhooks, CORS, endpoints anyone can call, unused and very large files, localhost addresses, a one-writer target with two writers, calls a target's list leaves out, retired rules, the Publishability group, and the design review of a blueprint) now come from the language table, under `health.<check>.*` keys with the same plural forms and placeholders as the rest of the map, so a German map shows them in German ("Zwei Schreiber für ein Ziel, das nur einen haben darf", "Namen aus deiner privaten Wortliste stehen in System-Dateien"); numbers and dates in them follow the language too. Every finding has a fixed `id`, and the fix requests, prompts for the agent, stay English. The scan now records the kind of a secret, the form of a CORS setting and a masked hint as data rather than English words, so one scan serves a map in any language. In English every finding reads exactly as before (one exception: "1 lines" in an unused file's note now reads "1 line"). See [Languages](docs/i18n.md#translating-the-findings).
- **"Not a problem" from 0.6.1 in the map's language, and in Publishability:** its button, dialog, notes and messages come from the language table, so a German map asks "Kein Problem?". The report it can open for the Floorplan developer keeps its labels English, like the fix requests, with the finding's title as the map shows it. A Publishability finding can be marked too: it then leaves that group's count by layer, on the map and in `PUBLISHABILITY  N findings in system, M in config`, and never touches the usual count; each of the group's findings now records `finds`, the number of places it counts.
- **Small fixes on the way:** "1 hours ago" and "1 lines" now read "1 hour ago" and "1 line", and the glossary no longer underlines a word inside a longer one when a letter like "é" or "ä" follows it.

## 0.6.1 (2026-11-01)

- **Fewer false alarms in Health** (thanks to the user who reported these):
  - **A password hash isn't the password:** bcrypt, argon2 and similar hashes are no longer reported as passwords, and neither is anything under a name like `ADMIN_PASSWORD_HASH`, including browser variables such as `VITE_ADMIN_PASSWORD_HASH`. The secret that makes a hash (`HASH_SECRET`) is still flagged, and so is a real key format under any name.
  - **An encrypted backup isn't an exposed one:** encrypted values in a `.env` file are left alone (dotenvx, sops, Ansible Vault, AWS KMS, HashiCorp Vault, age, PGP, OpenSSL and Fernet), and so are passphrase-protected private keys. A value left unencrypted next to them is still flagged.
- **Mark an issue "Not a problem":** a new button on each Health issue, with an optional reason. The issue moves to the bottom of the list and out of the count, and stays there when the map is rebuilt. It shows again if the same check finds something new in that file or the issue changes severity, and **Show again** undoes it. Your choices are saved in `floorplan/health-dismissed.json`. Exported copies keep the issue set apart but leave your reason out.
- **Report a false alarm if you like:** a box in the same dialog opens a GitHub issue for you to read, edit and send yourself, with a preview of exactly what it says. It never includes your code or any values, and nothing is sent unless you send it.

## 0.6.0 (2026-10-31)

- **Health catches the classic mistakes in AI-built apps.** Five new checks, each in plain words with a fix to paste:
  - **Secret keys sent to the browser:** an OpenAI, Stripe or Supabase service-role key (and others) in a `NEXT_PUBLIC_`, `VITE_`, `REACT_APP_` or similar variable, which every visitor can read. Keys that are public by design, like Supabase's anon key or Stripe's publishable key, are left alone.
  - **Supabase tables anyone can read and change:** tables whose row-level security is never switched on (or is switched off), worked out by replaying the migrations in order, so a table locked later or dropped doesn't count. Policies that let anyone add, change or delete rows are flagged too, as worth a look.
  - **Firebase rules that let anyone in:** Firestore, Storage and Realtime Database rules open to anyone, including "test mode" rules, with the date they stop working (or stopped).
  - **Stripe webhooks anyone could fake:** code that acts on events like `checkout.session.completed` without checking Stripe's signature, so anyone could send a fake "payment succeeded".
  - **Servers that let any website call them (CORS):** a small note on its own, and worth fixing when login cookies are allowed along with it.
- **No more false alarm on Supabase's `config.toml`:** values like `"env(S3_SECRET_KEY)"` read a setting from the environment, so they're no longer reported as a key written into the code.

## 0.5.0 (2026-10-31)

- **Fits phones and tablets:** the top bar wraps instead of running off the screen, the details open as a sheet at the bottom of a phone (tap a box to see them), the long description under the title folds to a line with More / Less, and every control is at least 44 px to tap. Nothing changes with a mouse at 1000 px and wider. Requested in #18 and built by @menachem-kurkus in #19.

A mouse, a trackpad and the wheel work exactly as before. Built by @menachem-kurkus in #24.
- **No hover tooltip after a tap:** a tap also sends the browser's hover event, so a card's tooltip popped up over the details sheet. Tooltips now show only for a mouse, and a tooltip stays inside a narrow window.

## 0.3.0 (2026-10-29)

- **Blueprints: plan it before you build it.** Floorplan still maps the code you have; now it can also start from no code at all. Share a PRD, a spec or a description of something you want to build, and Floorplan draws the map of what it would take: every part, file, endpoint and screen, how they connect, and the outside services they rely on. It's marked as planned (dashed cards and a **Blueprint** label), Health becomes a design review of the plan (endpoints anyone could use, decisions the PRD leaves open, loose ends), and each part has **Build this with Claude** (or Codex), a ready request to build it as planned. Switch the Ask bar to **Change** to shape the plan from the map ("also plan out refunds"): the map redraws with the new and changed pieces highlighted, and **Undo** puts it back. Design review items can be settled the same way with **Resolve on the map**: an open question just needs your answer. Once the code exists, the map can switch to the real code.
- **Bracketed folder names** like Next.js' `[id]` and `[...slug]` can be written as they are in `architecture.json` path patterns; they match that folder exactly.

## 0.1.0 (2026-10-27)

First release.

- **The map:** an interactive node graph of a codebase, from the whole app down to single files and endpoints. Every part has a plain-English name and description. It works across several repos side by side.
- **Connections:** imports, and web requests matched to the server endpoints they reach, including URLs built in variables, nested template strings and small request helpers. Flask blueprint and Express router prefixes are resolved, nested mounts included.
- **Screens:** detects an app's pages (Next.js, React Router, Vue, SvelteKit, Remix, Nuxt, Astro, Expo, Angular, TanStack) and shows everything behind each one.
- **Health check:** passwords and keys in code, endpoints anyone can use without signing in, unused files and very large files, each with a ready-made fix prompt. Secret values are never stored.
- **Ask:** questions answered as a mini-map with a walkthrough, through the Claude Code CLI or the Claude app.
